# D3D12.X interfaces and unified memory

What the console's D3D12.X interfaces look like, where each fact comes from, and how `d3d12_xs`
and `xmem` implement them. Claims about the console DLLs bundled with titles cite an address in a
binary; re-check any of them with `nix run .#d3d12x-probe -- dis <dll> <address>`.

Sources:

- `XboxBvhBuilder.dll` (BVH): its exports carry mangled parameter types (`ID3D12Device11*`,
  `ID3D12GraphicsCommandList4/6/8*`), so the object behind every vtable call is known.
- `amd_fidelityfx_upscaler_xbox.dll` (FFX): device calls identified by their IID argument and
  argument shape.
- Other projects, facts only: [ScarlettX](https://github.com/Freminet/ScarlettX) (**SX**, traced
  from a retail Unity title; no licence, so no code is taken from it), XValkyrie (a June 2020
  kit's `d3d12_x.h` tables compared with PC, GPL-3.0), TomBox (from an Unreal Engine 5 title's
  RHI), Leonida, xcl, TuxBox, xbox-emulator and
  [Xbox2Windows](https://github.com/R0Y00/Xbox2Windows) (MIT).

```sh
nix run .#d3d12x-probe -- slots path/to/title/XboxBvhBuilder.dll   # typed slots + direct field accesses
nix run .#d3d12x-probe -- iids path/to/title/*.dll                 # GUIDs and the vtable slot they feed
```

## IIDs

The console DLLs pass the **PC D3D12 IIDs**, byte for byte, to the device methods that take them:
`ID3D12Resource`, `ID3D12DescriptorHeap`, `ID3D12RootSignature`, `ID3D12CommandSignature`,
`ID3D12PipelineState`, `ID3D12Heap`, `ID3D12RootSignatureDeserializer`, and `ID3D12Device`
(QueryInterface, FFX 0x18000de66).

Console-only IIDs (XValkyrie, June 2020 kit): ID3D12Device8 {728f1fa2-ea11-4a9f-9b52-9b42a484d5c9},
command list 6 {c3827890-4024-474c-98cf-645b51dc4874}, DMA command list
{30bc77b9-8379-4b25-95de-b8588c42275d} (list type 16), IGraphicsUnknown
{aceeea63-e0a9-4a1c-bbec-71b2f485f758}. The proxies answer QueryInterface for them by value
(Device8 on the device, list 6 and DMA on lists, IGraphicsUnknown on all); any other IID
vkd3d-proton refuses is logged. Titles also import interface IDs as data from the system
partition's DLLs; `d3d12_xs` exports them.

## Layouts depend on the title's SDK

`D3D12XBOX_CREATE_DEVICE_PARAMETERS.Version`, the first u32 of the creation parameters, picks the
layouts (ScarlettX, from each SDK's debug driver). `D3D12XboxCreateDevice` logs the parameters
(version, debug flags, ring size, scratch sizes, prefer-WARP).

**Older lists (before 0x20004)**, following XValkyrie's June 2020 tables: PC + 4 up to 55, PC's
query methods at 28-31 (PC 52-55: `BeginQuery(heap, 0, 0)`, timestamps with `(heap, 2, 2)`), PC
56-59 (markers, ExecuteIndirect) in place at 56-59, FlushPipelineX (67) and OMSetDepthBoundsX (68)
ignored, DispatchX 78, CopyResourceX 84, PC 60-76 at 105-121, RSSetShadingRate,
RSSetShadingRateImage and DispatchMesh at 124, 125 and 127. 62 traps.

**Memory writes and waits** (xcl): Write32/64BitValueBottomOfPipeX `(address, value)` at 69/70,
Wait32/64BitValueX `(address, comparison, value, mask, flags)` at 71/72, Write32/64BitValueTopOfPipeX
at 88/89 and Write32BitValueBottomOfShaderX at 90 (two later from 0x20004). CopyMemoryToMemoryX
`(destination, source, size, flags)` at 60 (62 from 0x20004) copies title memory: it is kept with
the list as one of its CPU writes below and made in the same order. DispatchX `(x, y, z, flags)`
at 78 (80) is dropped (`REBOX_DISPATCHX=1` runs it as Dispatch; the ray tracing builder's, they faulted the GPU), CopyResourceX `(destination, source, flags)` at 84 (86) is CopyResource,
the pipeline syncs `(flags, control, address, size)` at 129/130 (131/132) are full global
barriers, as vkd3d-proton orders nothing in a list without one (`REBOX_PIPELINE_SYNC=0` ignores
them), a list's first ExecuteIndirect is preceded by a barrier into indirect arguments unless it
had one, so vkd3d-proton reads the arguments where the draw is rather than ahead of the list
(`REBOX_INDIRECT_BARRIER=0` leaves that out), and DriverHintX `(feature, value)` at 99 (101) returns 0, as
the host driver takes no hints (shapes: VIctory, GPL-3.0, facts only). A write to GPU memory
is WriteBufferImmediate (MARKER_OUT at the bottom of the pipe, MARKER_IN at the top). A write
anywhere else is kept with the list and made by a worker thread once a fence the queue signals
after the submission passes, in submission order (xcl's cpu_writes). Waits are evaluated on the
CPU before the list's submission, `(memory & mask) <comparison> value` with D3D12_COMPARISON_FUNC,
for up to 2 s, unless an earlier write in the same list covers the address. A submission of several lists
is split before each list that waits, so its waits come after the earlier lists in the batch (and
their writes) as on the console: hoisted before the whole batch, a wait for a counter an earlier
list writes had the queue wait on itself until the timeout. The writes a list records before a wait are made
before the wait too (fences signalled on the queue, CPU writes once the queue gets there): one
title's compute lists write a counter and then wait for one the graphics queue writes after
waiting for the first. The CPU writes of different queues don't wait for each other.

**Lists from 0x20004**: two methods were added at 59 and 60, and every named method from 61 on is
the older one two slots later. Everything one title's bundled DLLs call fits: FSR's
ExecuteIndirect at 61 (PC 59 plus two), the BVH builder's write/wait calls at 71, 73 and 90, and
141-148. So these lists get: 0-55 as in the older table, 56-58 the PIX markers, 59 ExecuteIndirect in place
(Unreal 5 calls it there), 60 trapping, 61 ExecuteIndirect, 85 CopyTextureRegionX, 107-123 PC
60-76 (render passes, ray tracing: 119-121 acceleration structures, 122 SetPipelineState1, 123
DispatchRays), 126/127 shading
rate, 129 DispatchMesh, 146 Barrier, 148 the embedded allocator.

**PSOs** outlive the title's last Release by 8 presents: on the console a PSO's shaders are
the title's memory, so titles release PSOs that work in flight still uses, which on the desktop
frees the Vulkan pipeline under the GPU. Release (patched in vkd3d-proton's PSO class) still
returns the title's count.

**Fences** (device slot 36) are proxies: slot 12 of the newer layout returns the address of the
fence's completed value, which a title reads and sleeps on (xcl). Each fence asked gets a cache
line that a thread keeps equal to GetCompletedValue, woken by an event armed for every queue
Signal of it; a CPU Signal refreshes it at once. The console's SHARED flag is dropped (the
desktop's shared fences are cross-process ones). Queue Signal and Wait unwrap the fence.

**Queues** come in two layouts, chosen by the game OS a title ships with, not the version (xcl):

- older: PC through 17 (Signal 14, Wait 15, GetTimestampFrequency 16, GetClockCalibration 17),
  then console methods 18-25 (PIX capture, SuspendX, ResumeX, **SignalX at 23** with `(fence,
  value, flush flags)`), **GetDesc 26**, page mapping 27-29, **PresentX 30**, SetHDRToneMapperX 31,
  and 35 an ExecuteCommandLists `(count, lists, value, flags)` (the target title submits its
  batches there; the value and flags are unknown);
- newer (ScarlettX): two methods ahead of Signal, so Signal 16, Wait 17, SignalX 25, GetDesc 28,
  PresentX 32, and CopyPageMappingsBatchX 31 (29 + 2: VIctory; maps a pool's physical pages at
  the batches' addresses: `{destination, count, ranges}`, a range `{kind, start, count}` in 64 KiB
  pool pages, kind 0 in order, 1 one page repeated, 2 unmap, 3 leave; xmem `ReboxMapPhysicalAlias`).

Nothing at device creation tells them apart, but Signal and Wait take a fence and the older 16/17
never do. So every queue starts on the older table; slots 16 and 17 dispatch on their first
argument (one of vkd3d-proton's fences: Signal/Wait, and the newer layout from then on; anything
else: the clock methods), 25 and 32 are SignalX and PresentX once the newer layout is known, and
lists made after that get the 0x20004 table.

## Inline fast paths: title code writes into our objects

D3D12.X headers inline the hot command-list methods, so title code reads and writes **fields of
the command-list object** and only calls the vtable when a buffer is full. From BVH 0x180020ea0,
which inlines SetPipelineState, SetComputeRootSRV, SetComputeRoot32BitConstant and Dispatch:

| Field | Use |
|---|---|
| `+0x18` | write cursor (a `BYTE*`) |
| `+0x28` | limit for a 16-byte Dispatch record |
| `+0x30` | limit for other records; at or past it, call the vtable method instead |
| `+0x140` | "root arguments dirty" byte |
| `+0x141` | copied from PSO flags bit 20 |
| `+0x143` | checked before choosing the Dispatch header |
| `+0x344 + 4*i` | per-root-parameter record header (one dword each) |
| `+0x544`..`+0x563` | copy of the bound PSO's 32-byte record |

PSO objects are read too: `pso+0x10` (a 28-byte record copied into the stream) and `pso+0x20`
(flags). The records the title appends:

- **SetPipelineState**: the 28 bytes from `pso+0x10`.
- **Root SRV/CBV/UAV**: `hdr[i]` + 64-bit GPU VA (12 bytes). Root constant: `hdr[i]` + value
  (8 bytes). If `hdr[i] & 0xC0000000` is zero, the title also sets `+0x140`.
- **Dispatch**: `0x4002C400` if `+0x140` or `+0x143` is set, else `(0x1000BA00 | flag141) << 2`,
  then `x, 1, 1` (16 bytes). Then it clears `+0x140`.

So `d3d12_xs` hands out its own command-list objects, never vkd3d-proton's, and keeps 0x1000
zeroed bytes after each proxy's vtable pointer: cursor == both limits == 0, so every inline path
sees a full buffer and calls the vtable method, and the unconditional writes (`+0x140`,
`+0x544`) land in the zeroed block.

**The device has inline paths too** (XValkyrie). A flags byte at device +0x18 says whether
`CreateConstantBufferView` (17) and `CopyDescriptorsSimple` (24) must be called. When it's zero
the title writes the CBV's V# itself (address | `0x0010000000000000`, then size/16 |
`0x0002403C00000000`; a null one is `0x0002403C00000001`) and copies CBV_SRV_UAV/RTV/DSV
descriptors as memory, 16 bytes at a time; +0x10 holds a null-buffer address. The device proxy
sets the byte to 1 (the smoke test checks it).

## Struct returns: result first

Console titles call methods that return a struct with the result pointer first and the object
second, the C convention (`GetResourceAllocationInfo`: `rcx` the result, `rdx` the device, then
the mask, count and descs), where PC's MSVC member functions put the object first. 8-byte structs
(descriptor handles, `LUID`s) come back in `RAX` instead. The proxy accepts both orders, telling
them apart by which argument is the object: device 25 and 26, queue `GetDesc`, and resource
`GetDesc` (slot 10, patched in vkd3d-proton's shared resource vtable).

Console feature structs can be sized differently: the console's
`D3D12_FEATURE_DATA_D3D12_OPTIONS` is 64 bytes against PC's 60. `CheckFeatureSupport` (slot 13)
fills the PC struct and copies back what fits.

## Root signature flags

Console root signatures may carry Xbox-only flag bits: 0x01000000 (`FORCE_MEMORY_BASED_ABI`
according to xbox-emulator, unverified), 0x02000000 and 0x80000000. Microsoft's PC
`D3D12CreateRootSignatureDeserializer` rejects them (Leonida). vkd3d-proton serializes and
deserializes them unchanged and ignores them at creation; the smoke test
(`test_xbox_root_flags`) checks all three. What they mean for the console's SGPR layout is
unknown.

## Texture tiling

Textures in a title's memory are Gfx10-tiled. The console resource desc's `Layout` gives the
swizzle mode (xcl, checked against `xg_xs.dll` on 29,700 descs, and TuxBox): from 0x100 it is
0x100 plus the AMD swizzle mode (0x100 linear, 0x105 `SW_4KB_S`, 0x10A `SW_64KB_D`); Layout 2,
or desc flag 0x08000000, is `SW_64KB_D`; Layout 0 is `SW_4KB_S` for a plain 2D texture. Other
arrays are `SW_64KB_D`, cubemaps (and 6-slice arrays) and volumes `SW_4KB_S`, as a census of one
title's texture pools shows (Leonida). `title_textures.c` applies these (`REBOX_TEXTURE_SWIZZLE`,
README) and logs each distinct layout.

AMD addrlib (Mesa, MIT), created as Navi21 (family `FAMILY_NV`, external revision 0x29,
`gb_addr_config` 0x444), detiles both modes: its mip chains match bcpack-rs's measured layout of
retail pools (total size, first mip in the tail, every level's offset, for 256x256x9,
1024x512x11, 64x64x7, 2048x2048x12 and 300x200x9 in both modes), and the BC1 block orders
bcpack-rs measured (`xyxxyyxyxyxyx` in 64 KiB tiles, `xyyxxyxyx` in 4 KiB) are exactly
`SW_64KB_D` and `SW_4KB_S` for 8-byte elements.

Arrays: addrlib puts slices outermost (each slice a whole mip chain, tail first), and cubemaps are
stored that way. 2D arrays in the pools are stored **mip-major** (Leonida, pixel-validated): the
tail of every slice first, then each mip with all its slices. A pool entry is the texture's
memory image, so a title that streams it in unchanged has mip-major arrays in memory, and
`title_textures.c` reads them that way: each subresource is the one-slice layout at its offset
times the slice count, plus the slice times its size in one slice.
`REBOX_TEXTURE_ARRAYS=slice-major` reads addrlib's order instead.

`helpers/textures/texcheck.py` checks this on real pools through `d3d12_xs`'s own detiler: every
sampled 2D texture (467 over 57 pools) and all 81 cubemaps match Leonida's decoder, the 39 arrays
match mip-major (37 of them differ slice-major), and 2 of the 3 volumes match. The third
(256x32x8, 2-byte R16_FLOAT) differs: addrlib's reading is far smoother along y and z than
Leonida's, whose 2-byte volume pattern rests on that one texture.

## Texture changes: written pages

A placed texture is a copy of title memory, so a change there has to be found and uploaded
before the next submission. DirectStorage writes are reported (`ReboxTitleMemoryWritten`);
CPU writes by the title (a video decoder filling R8 planes, a glyph atlas) are not.

- **Write-watched memory.** xmem reserves `XMemVirtualAlloc`'s plain reservations and
  `XMemAlloc`'s page allocations with `MEM_WRITE_WATCH`. Before each submission
  `title_textures.c` asks for the 4 KiB pages written since the last one (`GetWriteWatch` with
  `WRITE_WATCH_FLAG_RESET`), over the span of each reservation its textures lie in, and makes the
  textures on them dirty through the 64 KiB page index; they are uploaded with the rest, up to 64
  a submission. These textures are not fingerprinted. As xcl (ivall/xcl, GPL-2.0-only,
  `title_textures.rs`), and VIctory (GPL-3.0, facts).
- **Wine** honours `MEM_WRITE_WATCH` in `NtAllocateVirtualMemory(Ex)` (so through `VirtualAlloc2`
  too) for plain reservations; `GetWriteWatch` needs the range inside one reservation. With
  Linux 6.7 on it uses the kernel's tracking (userfaultfd write-protect, `PAGEMAP_SCAN`): no
  faults, and writes by system calls are seen. Otherwise pages are read-only after a reset and
  ntdll's fault handler notes the first write (before any vectored handler), with its own reads
  (`NtReadFile`) handled around it. Either way the system writing there doesn't fail, which a
  read-only guard would. xmem checks once that a write is seen; if not, nothing is watched.
- **Write-tracked physical-page views.** Section views can't be write-watched, so xmem tracks
  them itself (`xmem.c`, "Write tracking"). When a texture wholly in views is registered, and
  before each upload reads it, `title_textures.c` asks xmem to arm its memory
  (`ReboxTrackPages`): each 64 KiB unit (the physical page size; 4 MiB pages per 64 KiB) is made
  read-only at every address its page is mapped at. The first write to one faults; xmem's
  vectored handler notes every address of the unit dirty, makes them writable and lets the
  write go on. Before each submission the dirty ranges (`ReboxTrackedDirty`) make the textures
  on them dirty. Arming comes before the upload's read, so a write is either in what is read or
  faults again afterwards. Also noted dirty: a page mapped anew (`XMemMapPhysicalPages`,
  `ReboxMapPhysicalAlias`; a view of an armed unit is protected as it is mapped), writes xmem
  makes through a page's home view (`ReboxWritePhysicalPages`, a copy written back at
  unmapping), and an armed unit made GPU memory in place. A system call writing into a read-only
  view fails rather than faulting (Wine's `ReadFile` returns `ERROR_NOACCESS`), so the title's
  `ReadFile`/`ReadFileScatter` (import_fixup) and DirectStorage's requests hold their buffer
  writable for the write (`ReboxPrepareWrite` to `ReboxFinishWrite`: disarmed, not armed again
  meanwhile, noted dirty when done; without the hold, the upload the disarming caused armed the
  pages again mid-request, the request failed and the title read data that never loaded);
  `XMemVirtualQuery` reports armed pages writable. A unit mapped
  as a copy (no placeholder there, or memory made GPU memory in place) isn't tracked; a texture
  with one is fingerprinted, and tried again at its next upload. Tracked textures aren't
  fingerprinted every submission (the hot check) or in the round robin, except as a safety net:
  each at most every 4 s. VIctory guards view memory the same way (facts only); it misses writes
  through another view of the same pages, which arming every address of a page covers.
  `REBOX_TEXTURE_TRACKING=0` turns it off.
- **Not watched or tracked:** GPU memory chunks (`XMemAlloc`'s GPU types), and title memory
  adopted as GPU memory (`gpu_memory_adopt`): the Vulkan driver's mapping replaces the pages, and
  the kernel's write watch skips it without reporting anything, so those spans are left out of
  the asking and their textures are fingerprinted (round robin, and every submission once
  rewritten, within `HOT_BUDGET`; ones presumed hot, a single uncompressed mip uploaded once,
  in turns, 1-byte texels (glyph atlases, video planes) apart from the rest, each turn starting
  where the last stopped: from the newest only, a world's new textures took the budget and an
  early glyph atlas was never checked). Sampling isn't tracked per submission (the GPU reads
  descriptors from title memory), so they aren't hashed only when sampled.
- A reservation the title releases without `XMemVirtualFree` makes `GetWriteWatch` fail; its
  textures are then uploaded once and fingerprinted. `REBOX_DIRTY_PAGES=0` turns watching off.

## Unified memory: GPU VA == CPU VA

Console titles treat GPU virtual addresses as CPU pointers:

- BVH 0x180019c69: a `D3D12_GPU_VIRTUAL_ADDRESS` from the build desc goes straight into
  `XMemVirtualQuery` as a CPU address, which must then be `MEM_COMMIT`, readable, with
  `(info+0x30) & 3` (a GPU-access field after the `MEMORY_BASIC_INFORMATION`) set.
- Command-list slot 148 returns a CPU pointer that the title fills and then binds as a root SRV
  address (0x180020ed6 → 0x180020f80).
- FFX copies shader bytes into `XMemAlloc` memory and passes that pointer in a PSO desc
  (0x18000565d).

`XMemVirtualQuery` is `(HANDLE process, const void *address, info*)` with a 0x40-byte info
struct. Titles store one address and use it from both sides, and the GPU loads addresses from
memory (BVH nodes, bindless tables, ExecuteIndirect arguments), so an offset between GPU and CPU
addresses can't work: GPU-visible memory has to sit at the same address for both.

### Getting identity mappings out of Vulkan

vkd3d-proton derives every GPU VA from `vkGetBufferDeviceAddress`, so buffers need a device
address equal to the CPU address. `tests/gpuva_probe.c` (native Linux, `make build/gpuva_probe`)
tries these routes:

| Route | How | lavapipe | RADV 26.x, Radeon 890M |
|---|---|---|---|
| import | `VK_EXT_external_memory_host` on the xmem range, plus capture/replay with `opaqueCaptureAddress = ptr` | identity (llvmpipe uses host pointers) | **no**: the requested address is ignored (`0xffff800100200000`) |
| placed | allocate, read the BDA, map at that CPU address with `VK_EXT_map_memory_placed` | extension missing | **no**: the BDA is in the GPU's upper half (`0xffff8…`), kernel space on the CPU |
| replay-low | ordinary allocation with `opaqueCaptureAddress = base`, then a placed map at `base` | skipped | stock: **refused** (`VK_ERROR_INVALID_OPAQUE_CAPTURE_ADDRESS`); **`.#radv-rebox`: identity**, device address `0x200000000000` as requested, GPU writes visible at the same CPU address |
| replay-high | as replay-low, requesting `base \| 0xffff800000000000`, mapped at `base` | skipped | works, but as an offset address |

The refusal is RADV policy: `radv_amdgpu_bo.c` passes `AMDGPU_VA_RANGE_HIGH` on every VA
allocation, so libdrm's `amdgpu_va_range_alloc2` uses its upper-half manager, which can't satisfy
a lower-half `va_base_required`. `patches/mesa-radv-low-va-replay.patch` drops the flag only when
the replay address is non-zero, below 2^47, and the allocation isn't 32-bit. Such an address also
keeps its own alignment where it isn't aligned to what RADV asks (`max_alignment`, 256 KiB, for every
allocation; the 2 MiB PTE fragment for allocations of 2 MiB and more), which libdrm would refuse;
a title's memory is only 64 KiB-aligned. Ordinary allocations
and genuine capture/replay (always upper half) are unchanged. The flake builds it as
`.#radv-rebox` (Mesa 26.3.1, RADV + lavapipe only).

```sh
nix build .#radv-rebox
VK_ICD_FILENAMES=$PWD/result/share/vulkan/icd.d/radeon_icd.x86_64.json build/gpuva_probe
```

### Identity memory

1. **xmem.dll** reserves `REBOX_GPUVA_WINDOW` (default 1 TiB at `0x200000000000`) at load, so
   Wine never hands that range out.
2. **xmem** sends GPU-visible memory types (`memory_type != 0`) to **d3d12_xs**'s
   `ReboxGpuAlloc`. It falls back to `VirtualAlloc` if d3d12_xs is unavailable, if
   `REBOX_GPU_MEMORY=0` is set, or under the loader lock.
3. **`ReboxGpuAlloc`** (`gpu_memory.c`) suballocates 64 MiB custom heaps (`WRITE_BACK`, `L0`) on
   the one device the title also gets from `D3D12XboxCreateDevice`. Each heap is spanned by a UAV
   buffer and mapped, so vkd3d-proton knows every byte as a resource and resolves raw VAs into it.
   `XMemVirtualQuery` and `XMemFree` consult its table.
4. **`VK_LAYER_REBOX_gpuva_identity`** (`layers/gpuva_identity.c`, host side, under
   winevulkan): on `vkCreateDevice` it enables `bufferDeviceAddressCaptureReplay` and
   `VK_EXT_map_memory_placed`; every host-visible `vkAllocateMemory` gets a capture/replay device
   address from a window allocator, and `vkMapMemory` maps it at the same CPU address. Unmaps are
   deferred to `vkFreeMemory`, which leaves the range reserved. Whole allocations are
   identity-mapped, so vkd3d-proton's suballocations are too. If the driver refuses the address
   (stock RADV), the layer logs once and passes allocations through.
5. **`rebox-run`** loads the layer and, on AMD GPUs, points `VK_ICD_FILENAMES` at `.#radv-rebox`.
6. **Title memory in place.** A title also places buffers over memory it got itself (the target
   title: `CreatePlacedResourceX` of a 174 MiB buffer at an address of its own, then root
   descriptors and vertex fetches inside it). `gpu_memory_adopt` makes such a range GPU memory where
   it is (up to 256 MiB of the committed run around it, 64 KiB-aligned, touching other chunks;
   where less than 2 MiB is free between chunks or the run's ends, a span down to 64 KiB fills it,
   kept whole by vkd3d-proton patch 0033, which asks d3d12_xs's `ReboxHeapWhole` before it
   suballocates a buffer heap under 2 MiB; `REBOX_ADOPT_SMALL=0` keeps the old 2 MiB least): it asks the layer through a mailbox (the window's last 64 KiB, committed by xmem,
   `layers/gpuva_mailbox.h`; `REBOX_GPUVA_MAILBOX=1`, which `rebox-run` sets) for the next
   allocation of that size at that address, and creates a CPU-visible heap. The layer gives it that
   device address, maps it somewhere else first, copies the title's bytes in and then maps it over
   the title's pages in one `mmap`, so other threads never see them empty. While it copies, the range
   is read-only and the mailbox names it: xmem's exception handler holds a write there until the
   new pages are in place and then retries it in them, so no write is lost. The heap
   becomes a GPU-memory chunk, so placements, root descriptors and memory writes there resolve to
   it. Adopted memory is never freed; if the layer or driver declines, the title's pages stay as
   they were and the buffer gets its own memory. Vertex and index buffers are bound by address
   alone (`IASetVertexBuffers` 48, `IASetIndexBuffer` 47), and vkd3d-proton binds nothing at an
   address no heap or resource covers ("VBO VA that does not exist", 100,000+ times a run for the
   target title): a bound range of title memory (4 GiB to 2^46, outside the window) is adopted
   then too.
7. **Below 2^46.** The console's addresses are 46-bit, and a title packs them so: with its memory
   where Wine puts big reservations, near the top of the 47-bit user space, the GPU faulted at an
   adopted buffer's address with bit 46 cleared. xmem asks every new reservation, its own and the
   title's `VirtualAlloc` (an import it replaces), between 4 GiB and 2^46 with `VirtualAlloc2`'s
   address requirement (below 4 GiB is RADV's 32-bit range, or below its VA space).

RADV behaviours the layer works around:

- **Guard page:** on GPUs with the SMEM out-of-bounds erratum, `radv_bo_create` maps one extra
  page past each allocation (`RADEON_FLAG_VM_PAD_1PAGE`), so the window leaves a gap after every
  allocation.
- **Lazy VA release:** a freed allocation's GPU VA range isn't released at once, so reusing it
  straight away is refused. The window allocator is next-fit and reuses ranges only after
  wrapping around; on a refusal for a memory type that has worked before, it skips 256 MiB and
  retries.
- **32-bit memory types** (descriptor buffers, device-generated commands) stay in RADV's own
  range: their first refusal marks the type as never-identity, and later allocations of it pass
  straight through. Titles don't reach that memory by pointer.

On the 890M every `ReboxGpuAlloc` heap is identity-mapped (the first chunk at `0x200000000000`),
including heaps allocated right after a free; `d3d12_xs` logs whether the first heap is. The
device proxy also creates DEFAULT-heap buffers, and DEFAULT heaps that hold only buffers, as
custom `WRITE_BACK`/`L0` heaps (slots 27, 28 and 76), which the layer identity-maps as well; on an
APU that memory is system RAM either way. Textures and mixed heaps keep ordinary upper-half GPU
VAs.

### Xbox texture layouts

`D3D12_RESOURCE_DESC.Layout` values from 0x100 up are console tilings (0x101 is the FidelityFX
recurrent texture's, per Xbox2Windows). Every path that takes a resource desc maps them to
`D3D12_TEXTURE_LAYOUT_UNKNOWN` and logs each value once: device slots 25, 27, 29, 30, 38 and 76.
The layout matters for textures whose memory the title addresses itself ("Texture tiling").

## Descriptor heaps in title memory

On the console the runtime allocates a descriptor heap's memory with `XMemAlloc`, object type 4
and the D3D allocator (128), and xmem passes every `XMemAlloc` to the title's exported
`__XMemAllocationHooks__` (alloc, free) without an `XMemSetAllocationHooks` call. A title can so
give a heap memory of its own: the target title registers an address and size with its hook for
the D3D allocator, makes its main CBV/SRV/UAV heap, and asserts that the heap's CPU start is that
address. Here:

- xmem uses a title's exported hooks for `XMemAlloc`/`XMemFree` (a hook calling back in gets the
  defaults);
- `d3d12_xs` allocates each CBV/SRV/UAV and sampler heap's memory the same way for titles with the
  export, and returns it as the heap's CPU start;
- the title's CPU handles in such a heap are translated to vkd3d-proton's in every call that takes
  one (view creation, `CopyDescriptors*`, `ClearUnorderedAccessView*`), and `ReboxShadowFind`
  reports title handles.

- the console-format shadow of such a heap is that memory itself, as the console keeps descriptors
  in the heap's memory, so descriptors the title writes there without the API are read too. A
  shader-visible heap's memory is made GPU memory in place (`gpu_memory_adopt`) as far as it can
  be, since translated shaders read descriptor tables from the GPU. Pages that can't be (the target
  title's main heap shares its pool with a buffer already made GPU memory) are read by the GPU from
  a mirror, refreshed from the title's memory before each submission.

## Proxies

`shims/d3d12_xs/proxy.c` implements the device, queue, graphics and copy command lists, and
descriptor heaps:

- **PC-compatible slots** go through a generated thunk: load the wrapped object from `+0x1000`,
  then jump to its PC slot, so argument lists don't need to be known.
- **Slots that differ** have C implementations, listed in `proxy.c`'s slot tables: on the device
  those that create or describe objects (8, 10-14, 17-19, 22-30, 38, 41, 43, 44, 48, 55, 60-62,
  68, 69, 73-76, 78-81, 86, 101, 115), on queues ExecuteCommandLists (unwraps lists), the
  ambiguous 16/17, SignalX, GetDesc and PresentX, on lists those taking heaps, GPU handles,
  barriers, copies, ray tracing and indirect arguments, and heap slots 8-10.
- **IDXGIDevice:** the console device answers `QueryInterface(IDXGIDevice..4)`, and titles use the
  answer unchecked: device → `GetAdapter` (+0x38) → `EnumOutputs` (+0x38), whose output goes to
  `SetFrameIntervalX`, and the adapter's parent `IDXGIFactory2` (ScarlettX, XValkyrie).
  `shims/d3d12_xs/dxgi_device.c` answers: its adapter is DXGI's (DXVK's) first, other methods give
  harmless answers, and `QueryInterface` for anything else goes back to the device proxy.
- **Every other slot** traps: it logs the slot and arguments once and returns `E_NOTIMPL`.
- **Not proxied:** resources, heaps, PSOs, root signatures, fences and allocators. Their vtables
  match PC as far as is known. Their `GetDevice` (slot 7) is patched in vkd3d-proton's shared
  per-class vtables to return the device proxy; vkd3d-proton returns one device per adapter, so
  every child of it is covered. The classes are found by creating one probe object of each; PSOs
  are patched on the first `CreateGraphics/ComputePipelineState`.
- **Topology:** the console's rectangle lists (topology 17) reach vkd3d-proton as 17, which patch
  0011 takes: a draw with deferred console graphics gets a pipeline with AnyPS5's rect-list stages
  (`BuildRectListShaders`, through `sa5_rect_list_stages` and d3d12_xs's `ReboxConsoleRectStages`),
  a tessellation control and evaluation pair over 3-point patches that makes each rectangle's
  fourth corner from the vertex shader's outputs, so it works for corners made from the vertex
  index too. The vertex and pixel stages compiled for a rect-list draw keep their AnyPS5 results,
  which the pair is built from (once per pair of stages); the control stage's fault buffer is the
  process's. If the pair can't be built, the draw uses the plain pipeline as a triangle list (each
  rectangle's first triangle), as do pipelines that aren't deferred console graphics. With
  `REBOX_RECT_LISTS=cpu` it's a triangle list from d3d12_xs instead, and a `DrawInstanced` with
  vertex buffers bound is drawn as two triangles a rectangle: each buffer's three corners are
  copied as v0 v1 v2, v0 v2 v3, with v3 = v0 + v2 - v1 made on the CPU word by word (a word the
  same in all three corners is kept, others are taken as floats), into the per-draw ring (after
  xcl, ivall/xcl#195).
- **Depth buffers as UAVs and their views:** a console depth buffer that is also a UAV is a depth
  target only here (`pc_desc`), created in `DEPTH_WRITE` where the title asks for the UAV state,
  and its UAVs are null views of the same dimension. Shader views that name a depth buffer's plane
  by a colour format (`R16_UNORM`, `R8_UINT`, `R32_FLOAT`) get the desktop's plane formats
  (`R24_UNORM_X8_TYPELESS`, `X24_TYPELESS_G8_UINT` in plane 1, `R32_FLOAT_X8X24_TYPELESS`,
  `X32_TYPELESS_G8X24_UINT`) (after xcl, ivall/xcl#163, #170).

## PresentX

`shims/d3d12_xs/present.c`:

- **Window and swapchain:** each queue that presents gets a window on its own message thread and
  a flip-model DXGI swapchain (DXVK's `dxgi.dll` over vkd3d-proton) on the inner queue, recreated
  if the plane's size or format changes. The swapchain has a frame-latency waitable object, and a
  frame is dropped rather than block the title when there's no free frame slot within 100 ms (a
  window the compositor isn't showing). `rebox-run` disables `VK_KHR_present_wait` and
  `present_wait2` for vkd3d-proton (`REBOX_PRESENT_WAIT=1` keeps them), because vkd3d-proton
  rebuilds the swapchain on the queue's submission thread after waiting for every outstanding
  present wait, which never ends for a hidden Wayland window.
- **Copying the plane:** `PresentX` copies plane 0 into the back buffer on the same queue, so it
  is ordered after the title's rendering, then presents with `REBOX_VSYNC` (default 1).
- **Formats:** RGBA8, BGRA8, RGB10A2 and RGBA16F families map to swapchain formats. Any other
  plane format (e.g. R11G11B10_FLOAT) is converted into an RGBA8 intermediate with `ReboxBlit`,
  clamping HDR values.
- **Finding the plane:** the qword at `plane_params+16` is the resource or a pointer to it; both
  are recognised by vkd3d-proton's resource vtable. The first call logs the raw params.
- **The plane's state** comes from tracking initial states at creation (device slots 27, 29, 30,
  76) and every barrier the title records (slots 26/15, and 146 by enhanced-barrier layout).
  Untracked resources are assumed COMMON.
- **Frame dumps:** `REBOX_DUMP_FRAMES` writes chosen frames as BMP (the converted image for other
  formats); the smoke test checks presents headless that way.

**Frame pacing** (`pacing.c`): a QPC clock stands in for the display's frame events. Origins fall
every interval × period from `SetFrameIntervalX` (16.67 ms until it's called), and each event
type sits at its `ScheduleFrameEventX` offset. A wait acts on an auto-reset event: it returns at
once if an occurrence passed since the last wait (the newest one, so a late title skips frames
rather than bursting), otherwise it sleeps until the next one on a high-resolution timer. A
timeout that would pass first returns `HRESULT_FROM_WIN32(ERROR_TIMEOUT)` (the console's code is
unknown). Tokens follow what XValkyrie found Unreal needs: `WaitFrameEventX` gives consecutive
tokens, `PresentX` names its frame's token in the first plane's first field, and
`GetFrameStatisticsX` reports rendering, presenting and display only for presented frames, from a
record per token. `ScheduleFrameEventX`'s list is `{u32 count; HANDLE *handles}` (TomBox: Unreal's
points at its RHI's flip-event field, which `RHIWaitForFlip` waits on); the handles are read
through it at each occurrence, and flag bit 0 stops signalling. `REBOX_FRAME_PACING=0` makes the
three methods no-ops.

## Other console behaviour

- **DirectStorage** (`shims/xcrdapi`, vtable after `dstorage_xs.h`: 5 `EnqueueSetEvent`, 12
  `EnqueueSignal`, 14/15 auto-submit): the console's queue submits by itself unless
  `SetAutoSubmitDisabled` says otherwise, so every enqueue runs.
- **Runtime** (XValkyrie): titles load `xgameruntime.dll` with LoadLibrary (QueryApiImpl,
  InitializeApiImpl, InitializeApiImplEx, UninitializeApiImpl, XErrorReport).
  `XSystemGetDeviceType` reads `HKLM\...\CurrentVersion\OEM\ConsoleMode` (0x64 Series X); a
  retail title crashes on "PC". Physical pages, emulated in `shims/xmem`:
  XMemAllocatePhysicalPages(flags, count *, pages *), XMemMapPhysicalPages(address, count,
  pages), XMemFreePhysicalPages(count, pages); `VirtualAlloc` with `MEM_LARGE_PAGES` or
  `MEM_4MB_PAGES` (0x80000000). `XMemVirtualAlloc` accepts the console's GPU protection bits
  (`0x2404`) without `MEM_PHYSICAL`.
- **Sizes** (XValkyrie): descriptor increments 32/16/112/128 (CBV_SRV_UAV, sampler, RTV, DSV); the
  Series command list is 0x560 bytes and inline SetPipelineState copies 32 bytes from pso+0x10 to
  list+0x540.

## Workarounds

- **Missing shader translations:** fallback shaders (README). So does a PSO whose bytecode looks
  like PC's (or came from the cache) but fails to compile: XboxBvhBuilder's shaders are Xbox DXIL
  calling `@xbox.*` intrinsics (americas-recomp), which vkd3d-proton rejects, so BVH builds are
  no-ops.
- **FidelityFX:** a stub `amd_fidelityfx_loader_xbox.dll` replaces the package's (through
  `rebox-run`'s shadow package directory). Its descriptor types and dispatch offsets were checked
  against the real upscaler's exports and provider vtable. Dispatch calls `d3d12_xs`'s `ReboxBlit`,
  a compute bilinear scale recorded into the title's list, which changes its compute root
  signature and PSO as real FSR does and restores the title's descriptor heaps.
- **Texture GPU VAs:** vkd3d-proton returns 0 for textures. The resource class's
  `GetGPUVirtualAddress` (slot 11, patched in its shared vtable) hands a texture GPU memory of
  its allocation size or console size, whichever is larger, registered as a title texture
  (`title_textures.c`): what the title writes there, tiled as on the console, is detiled into the
  texture before the queue runs, as for `CreatePlacedResourceX`. Render target, depth and UAV
  textures keep it as plain scratch, since the GPU writes those. `Release` (slot 2) frees it.
- **Mapping textures:** titles `Map` textures, which are in unified memory on the console.
  vkd3d-proton refuses a DEFAULT heap texture, so `Map` (slot 8) of a texture's subresource 0
  returns that same console memory, and `Unmap` (slot 9) marks it written so the next submission
  uploads it.
- **Audio:** XMA2 voices fail under WineGDK; `shims/xaudio2_9` handles them (README).

## Bringing up a title

`tests/manual-test.sh` reruns the hardware checks (patched RADV, layer, probe, Wine smoke test)
and keeps the log in `build/manual-test.log`. When a title crashes, `xmem.dll`'s fault report
(`REBOX_CRASH_LOG`) gives the exe RVA and stack to open in a disassembler; an access violation
inside the GPU window points at unified memory. `REBOX_SLOT_STATS=600` shows which proxy slots it
calls and how often: hot forwarded slots are where a wrong PC-equivalence assumption would hurt,
and trapped ones (`T`) are the next methods to identify. `d3d12x-probe` on the exe finds more;
without exported types, start from the call sites of `D3D12XboxCreateDevice` and
`CreateCommandList`.
